# OpenClaw 复刻项目全面检查提示词

将以下提示词原样交给目标 agent（Claude Code / 复刻的 harness），即可对 OpenClaw 复刻项目执行一次全面检查：

---

你是一名资深软件工程师，同时是一名资深 AI 应用开发工程师。请对当前 OpenClaw 复刻项目（AI 助手 / CLI agent 系统）做一次**全面检查**，产出缺陷优先、证据支撑的分级报告。

## 一、检查范围（逐项核对，全部维度都必须给出结论）

### A. 架构与工程（资深软件工程师视角）

1. **架构设计与分层**：模块是否职责单一、边界清晰；是否遵循依赖倒置；错误边界是否明确；模块间是否通过接口通信；是否支持可插拔架构；异步模型是否合理。
2. **Agent 循环**：`while stop_reason == tool_use` 主循环是否正确实现；循环内是否混入业务逻辑；hooks（PreToolUse/PostToolUse/Stop）是否承担横切关注点；退出条件是否完备、有无死循环风险。
3. **代码质量**：命名语义、函数长度与单一职责、重复代码、类型系统利用、错误处理统一性、魔法数字/硬编码、注释是否解释原因。
4. **性能与资源**：同步阻塞、内存管理、资源泄漏、启动时间、并发安全、缓存策略。
5. **可靠性与容错**：优雅降级、重试策略、断路器、外部调用超时、状态恢复、数据一致性。
6. **可维护性与可测试性**：核心逻辑单测、LLM mock/stub、工具沙箱测试、端到端测试、测试可重复性、数据工厂与隔离。
7. **工程规范与 CI/CD**：Lint、Git Hooks、CI 流水线完整性、版本管理、分支策略、环境隔离。
8. **依赖与供应链**：依赖数量、锁定、安全扫描、typosquatting、SBOM、许可证兼容。

### B. 安全与权限沙箱（AI 应用工程师视角）

9. **命令执行安全**：approve/reject/auto-approve 机制、危险命令黑名单、shell 注入防护、执行超时、输出截断、只读/写入命令区分。
10. **文件系统安全**：路径穿越防护、workspace 边界限制、写入前确认、符号链接逃逸、敏感文件（.env/密钥）保护、TOCTOU 防护。
11. **Prompt 注入防护**：外部数据（网页/git log/命令输出/通道消息）是否用 XML tag 或分隔符隔离并视为不可信；是否检测指令覆盖；是否防御间接注入与编码绕过；System Prompt 是否防泄漏。
12. **权限模型**：分级权限（只读/读写/完全控制）、多层配置、deny 规则不可覆盖、未信任项目配置拒绝、敏感操作独立开关。
13. **纵深防御**：Schema 校验 → validateInput → Pre/PostToolUse Hook → 权限决策链 → 并发控制 → 沙箱/容器隔离，六层是否齐全。

### C. LLM 集成与 Agent 专项

14. **Prompt 工程**：System Prompt 结构清晰、Prompt 外部化、工具 schema 准确、prompt 回归测试、变更影响评估。
15. **Token 与上下文策略**：上下文窗口管理、截断保留 system prompt + 最近 N 轮 + 工具结果、文件读取大小限制与智能截断、token 监控告警、分层记忆、指针/摘要替代原始长内容。
16. **错误处理与降级**：指数退避重试、模型降级、JSON 解析失败修复/重试、请求去重、429 排队。
17. **流式响应**：SSE/流式输出、流中断优雅降级、thinking/tool_call/result 中间状态可见、取消请求支持。
18. **工具系统**：动态加载、统一 JSON Schema、依赖声明、命名一致；执行超时、结构化错误返回、工具调用链、并发安全、资源限制；风险等级声明、高风险工具强制确认、审计日志。
19. **会话与上下文管理**：历史持久化、会话恢复、多会话、压缩策略、项目元信息读取、记忆系统与质量过滤、索引增量更新。
20. **幻觉防控与输出质量**：不确定时主动承认、文件操作前确认存在、异常结果检测告警、事实核查、工具结果原样传递、Reflection 机制。
21. **幂等性**：重复执行同一指令是否安全；失败重试是否产生副作用叠加。
22. **成本控制**：单次请求 token 上限、死循环检测、每日/每月预算、缓存策略、工具调用次数限制、成本归因。
23. **可观测性与评估**：结构化日志、请求链路追踪、敏感信息脱敏、用量统计、质量指标、异常告警、成本看板、离线评测集、在线评估、A/B 测试。

### D. 通道与交付（OpenClaw 特有）

24. **通道适配层**：各消息通道（Telegram/Discord/Slack/CLI 等）adapter 是否统一契约、错误处理是否一致、消息丢失/重投语义是否明确。
25. **交付与路由**：消息投递是否可靠（重试/死信）、多 agent 路由是否正确、并发消息是否乱序、附件安全（类型/大小/恶意文件）。
26. **数据库与状态**：Schema 迁移是否可回滚、会话/任务/记忆持久化是否正确、并发写冲突处理、备份恢复。

## 二、证据规则

- 每个发现必须给出精确 `path:line` 引用和简短代码摘录。
- 说明触发路径、根因控制点、后果、影响与最小修复方案。
- 不得仅凭文档宣称某模块可用；不得虚构测试结果或严重级别。
- 无法动态复现的项，明确标注"未能动态验证"。

## 三、检查流程

### 第一步：建立整体认知（先通读，再深入）

**先通读，再逐模块深入，严禁一上来就扎进单个文件。**

1. **仓库目录结构**：用递归列出项目树，识别源码目录、测试目录、配置、docs、CI 等分布。
2. **README 与文档**：通读 README、docs 下关键文档，理解项目定位、架构说明、使用方式。
3. **入口文件**：找到并阅读主入口（main / index / CLI 启动文件），理解启动链路与模块装配顺序。
4. **依赖清单**：阅读 package.json / requirements.txt / go.mod / Cargo.toml 等，盘点依赖数量、类型（运行时/开发）、锁定情况与潜在供应链风险。
5. **项目规则文件**：读取 AGENTS.md / CLAUDE.md / tsconfig / 配置文件，理解约定与约束。
6. 基于以上形成**整体架构认知**（模块划分、数据流、agent 循环、通道接入点），再开始逐模块深入审查。

### 第二步：逐模块深入

7. 按上述 A–D 四组 26 个维度逐项审查，实际读取代码与调用点求证。
8. 在可行且安全的前提下运行 typecheck / lint / 测试 / 构建 / 冒烟检查。
9. 合理控制工具调用次数与 token 消耗；预算耗尽时立即进入报告输出。

## 四、输出格式（最终报告必须完整包含以下四节）

### 审查摘要

- 总体评级：优秀 / 良好 / 需改进 / 存在严重风险
- 关键发现数量：严重 X 项 / 风险 X 项 / 建议 X 项
- 已完成验证：类型检查、测试、构建、运行冒烟检查等

### 维度结论

对每个维度给出 `通过 / 风险 / 严重 / 不适用` 及一行依据。

### 详细发现

对每个发现：

#### [编号] 标题

- 维度
- 评级
- 位置（path:line）
- 问题描述
- 风险说明
- 修复建议
- 参考实现（如适用）

### 优先修复清单

列出优先级最高的 Top 5 修复项及理由。

## 使用说明

- 将上述提示词整体作为一次任务交给目标 agent 执行；可附加 `工作目录=<复刻项目根目录>`。
- 检查保持只读，除非用户明确要求修复。
- 若目标 agent 工具预算有限（如 MAX_TOOL_CALLS_PER_RUN=12），提示词"第二步：逐模块深入"第 9 步保证其能在预算内收尾并输出结构化报告。
